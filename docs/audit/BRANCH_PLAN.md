# Branch-plan coverage

Generated by `scripts/research/build_branch_plan.py` from the canonical
decision matrix. Output: `research/branch-plan.json`. Do not hand-edit the
JSON; rerun the builder.

## Inputs

| Input | Role |
| --- | --- |
| `src/data/meta.json` → `decisions` | 27 canonical decisions from the workbook's *Choices & Consequences* sheet. `journey1`, `journey1Result`, `futureOutcome`, and `futureJourney` are copied verbatim. |
| `src/data/items.full.json` → `items` | 2,325-entry catalog used for exact name → ID resolution. |

The workbook detail is already embedded in `meta.json`; no workbook cell was
re-read or reinterpreted for this pass.

## Method

1. Every decision is emitted in `meta.json` order with its verbatim
   `journey1`, `journey1Result`, `futureOutcome`, and `futureJourney` strings.
2. Reward names are extracted only where the matrix **names a concrete item**
   in a result/outcome sentence. Generic prose ("full dialogue", "expanded
   shop", "finale summons", "access") is not turned into an item.
3. Names are normalized (case, accents, apostrophes, punctuation) and matched
   against the catalog:
   - **exact** — one unique normalized catalog name;
   - **alias** — the only differences are an item-type suffix added by the
     decision text (documented in the JSON `aliases` array);
   - **unresolved** — no unique match. `itemId` stays `""`, and the reward
     carries `unresolved: true` plus a `reason`.
4. Availability is assigned **only** from the matrix. A reward listed in
   `journey1Result` is `journey-1`; a reward in `futureOutcome` follows the
   journey named in `futureJourney` (`NG+ — Journey 2` → `journey-2`,
   `NG++ — Journey 3` → `journey-3`). No reward was scheduled on a journey the
   decision text does not state.
5. `kind` separates acquisition rewards (`reward`) from ending prerequisites
   (`required`) and set-level names (`set`).

## Unresolved reward entries

These are **catalog-resolution gaps, not unavailability claims**. Each item is
still a real branch outcome in the decision matrix; the current
`items.full.json` catalog simply has no row that matches the normalized name.

| Decision | Reward | Reason | Catalog check |
| --- | --- | --- | --- |
| `BASE-001` | Alexander's Innards | No catalog row. | Searched `innard` across all 2,325 names; zero hits. |
| `BASE-003` | Ancient Dragon Smithing Stone | No catalog row. | Smithing stones are not part of this item catalog (the upgrade ledger is a separate workstream); no `ancient dragon smithing` name exists. |
| `BASE-006` | Eccentric's Set | Set-level name; catalog stores pieces only. | Components resolved: Hood, Armor, Manchettes, Breeches. |
| `BASE-006` | Ancient Dragon Smithing Stone | Same as BASE-003. | — |
| `BASE-007` | Unalloyed Gold Needle | No catalog row. | Searched `needle`; catalog has Sewing Needle, Frozen Needle, Thiollier's Hidden Needle and the Miquella's Needle note only. |
| `BASE-009` | Zorayas's Letter | No catalog row. | Searched `zoraya`; zero hits. |
| `DLC-003` | Ansbach's Set | Set-level name; catalog stores pieces only. | Components resolved: Attire, Boots, Manchettes. |

Set-level entries keep `itemId: ""` and `unresolved: true` because no set item
exists to point at; `componentItemIds` carries the resolved piece IDs so the
integration can still create completion scopes. Altered variants
(`Eccentric's Hood (Altered)`, `Ansbach's Attire (Altered)`) exist as separate
catalog rows and are deliberately not folded into the base set.

## JSON shape

Core fields follow `research/BEYOND_REDMAW.md`:

```json
{
  "decisionId": "BASE-001",
  "title": "Alexander, Warrior Jar",
  "journey1": "…",
  "futureOutcome": "…",
  "futureJourney": "…",
  "rewards": [
    { "name": "Shard of Alexander", "itemId": "GKI-PERM-BG-TAL-8B9A9A70FBDA88",
      "journey": 1, "availability": "journey-1" }
  ],
  "unresolved": false,
  "notes": ""
}
```

Additive fields: `game`, `category`, `journey1Result` (traceability);
`kind` (`reward` | `set` | `required`), `resolution`
(`exact` | `alias` | `unresolved`), `retained` (only present as `false` for a
reward spent in the same journey), plus `reason`, `candidateItemIds`,
`componentItemIds`, and `unresolved` on reward entries when relevant. Top-level
`counts`, `unresolvedRewards`, `aliases`, and `availabilityRule` support the
completion UI without recomputing coverage.

`kind: "required"` marks the three ending Mending Runes. They are prerequisites
for `END-002`/`END-003`/`END-004`, not branch rewards; `BASE-004` is the
acquisition decision for the Fell Curse rune. Consumers that only want granted
items should filter to `kind == "reward"`.

## Regeneration

```bash
python3 scripts/research/build_branch_plan.py          # rewrite JSON
python3 scripts/research/build_branch_plan.py --check  # fail if stale
```

The builder fails if the decision count is not 27, if a decision ID is missing
from or added to the reward spec, or if a declared set piece stops resolving
uniquely. This prevents silent drift when the decision matrix changes.
